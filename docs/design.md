# Design - jupyterlab_device_bridge_extension

The design of the first version as it is built. `docs/brief.md` says what is required; this file says how the server, the frontend and the CLI work together. Where this file and the code disagree, fix one of them in the same change.

## Parts

```
board → OS driver → browser tab ─┬─ main thread: grant dialogs, panel, status item, menu
                                 └─ dedicated Web Worker: device I/O + one WebSocket
                                        │  wss://<lab>/jupyterlab-device-bridge-extension/ws
                                 Jupyter server extension (DeviceManager)
                                   ├─ serial: one pty per port → <device_dir>/tty-…   → any serial tool
                                   ├─ monitor: ring buffer per port                   → CLI monitor read
                                   ├─ shim socket per port                            → LD_PRELOAD shim
                                   └─ REST                                            → CLI, Python client, pyusb backend
```

- **Main thread** - the only place that can open Chrome's grant dialogs (`navigator.serial.requestPort`, `navigator.usb.requestDevice`); owns every widget and reads the settings of the lab
- **Worker** - owns the WebSocket and every device object it gets from `navigator.serial.getPorts()` and `navigator.usb.getDevices()`; moves every byte
- **Server** - owns the virtual serial devices, the monitor buffers, the device table, the pending device requests and the USB relay
- **CLI and client** - talk to the server over authenticated loopback HTTP only

## Facts this design rests on

| Fact                                                                                                                                                                                                                               | How it is known                                              |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| A Blob-URL worker on `http://localhost` has `navigator.serial` and `navigator.usb`, is a secure context, keeps the page origin, resolves `getPorts()` and `getDevices()`, can construct a `WebSocket` and has `importScripts`      | probe in headless Chrome 155, 2026-10-12                     |
| The grant calls `requestPort` and `requestDevice` do not exist in a worker                                                                                                                                                         | same probe                                                   |
| pty facts (data both ways, baud visible on the master, open and close visible as `POLLHUP`, DTR and RTS calls refused with `ENOTTY`, parity dropped)                                                                               | brief, tested                                                |
| glibc's `tcsetattr` on a pty slave fails with `EINVAL` when the call asks for parity or for a data size other than 8 bits and changes nothing else. With a new baud rate in the same call it succeeds and the pty drops the parity | measured in this container with glibc 2.39, 2026-10-12       |
| Exclusive mode (`TIOCEXCL`) stays on a pty slave after the tool that set it closed the slave. Every later open of that slave fails with `EBUSY`                                                                                    | measured in this container, 2026-10-12                       |
| Chrome opens a grant dialog only inside a user gesture                                                                                                                                                                             | from knowledge, not tested; the code handles `SecurityError` |
| `close()` of a serial port discards the bytes the port has not transmitted yet. Closing its writable stream first waits until they are transmitted                                                                                 | Web Serial specification; not tested with a port             |

## Names and ids

- **tabId** - `crypto.randomUUID()` made by the worker, one per lab tab; `tab-<random hex>` in a page that is no secure context, where `crypto.randomUUID` is absent. The server accepts 1 to 64 characters
- **key** - what a tab claims. Serial: `s:<vid>:<pid>:<n>`; a port without USB ids uses `s:port:<n>`. `n` is the lowest index that no other port of that tab with the same ids has when the worker first lists the port. The port keeps its key for as long as the browser lists it. USB: `u:<vid>:<pid>:<serialNumber>`; `u:<vid>:<pid>:#<n>`, with `n` chosen the same way, when the device has no serial number or another device of that tab already has that key. Ids are 4 lowercase hex digits
- **name** - what programs use. Serial `tty-<vid>-<pid>`, non-USB `tty-port`; USB `usb-<vid>-<pid>`. The second device with the same base name gets `-2`, the third `-3`. Pattern `^[a-z0-9-]{1,64}$`; every handler validates it
- **key → name** is kept by the server for its lifetime, so a reload or a re-attach gets the same name and the same path
- **sid** - unsigned 16-bit number the server gives an attached serial device, used in binary frames
- **path** - `<device_dir>/<name>`, a symlink to the pty slave

## Device directory

- `DeviceBridge.device_dir` (traitlet), empty by default. The Jupyter config file is the only way to set it; no environment variable names the directory. For an empty setting `default_device_dir` chooses once at server start: `/run/devices` when the server's user owns it, or when it is missing and that user can write `/run`; else `/tmp/jupyterlab-device-<uid>`, with a log line. An image makes `/run/devices` for the server's user
- Created `0700`; before every use it must be a real directory owned by the current uid, else the server logs why and refuses the claim of the serial port
- Holds the symlinks `<name>` and the shim sockets `.shim/pts-<minor>.sock` (`0600`)
- **Lock** - the server takes an exclusive, non-blocking `flock` on the directory itself and holds it until it ends: at its start when the directory exists, else before it makes its first link. The lock adds no file, and the kernel releases it when the process ends, also when the process is killed. The lock is refused only while a live process holds it, so a server that gets the lock removes what a server that ended without its exit hook left there: every symlink in the directory that leads to a pty slave (a target under `/dev/pts/`) and every socket in `.shim`. Any other symlink, a directory, a regular file and the entry `.shim` itself stay
- **Lock refused** - another live server uses the directory. The server removes nothing and logs one warning that names the setting `DeviceBridge.device_dir`. It then holds no lock: a server that starts later and gets the lock removes its links and sockets too
- `/tmp` and not the home directory: a home on a network volume cannot hold a Unix socket. The CLI never guesses the path; `list` prints it

## Serial port in the worker

- **States** - `closed`, `opening`, `open`, `error`. Every operation on one port (open, close, reconfigure, signals, action, write) runs through one promise chain per port, so a write issued after a reconfigure reaches the port after the reopen
- **Open** - `port.open({baudRate, dataBits, stopBits, parity, bufferSize: 65536, flowControl: 'none'})`; then a read loop on `port.readable` that sends each chunk as a binary frame and keeps a writer on `port.writable`
- **Close** - close the writer, cancel the reader, release both locks, `close()`. The close of the writer waits until the port has transmitted the bytes it accepted; `close()` alone discards them. The read loop runs during that wait. The wait has no time limit: a port that does not transmit holds back every later operation on it. A writer that fails to close does not stop the close of the port
- **Reconfigure** - Web Serial takes settings only in `open()`: close as above, `open()` with the new settings, restart the read loop. No-op when the port is open with equal settings
- **Signals** - `port.setSignals({dataTerminalReady, requestToSend, break})`. Only a line that the command names with `true` or `false` is set
- **Actions**

| Action           | Steps on the port                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| `none`           | nothing                                                                                                           |
| `pulse-dtr`      | DTR false, wait 100 ms, DTR true                                                                                  |
| `pulse-rts`      | RTS false, wait 100 ms, RTS true                                                                                  |
| `esp-bootloader` | DTR false + RTS true, wait 100 ms, DTR true + RTS false, wait 50 ms, DTR false + RTS false                        |
| `touch-1200`     | close, open at 1200 baud, DTR false, close, wait 500 ms, open with the previous settings if the port still exists |

- **Removal** - the worker listens to `disconnect` and `connect` of `navigator.serial` and lists the granted ports again on each event. A port that the browser no longer lists is released with reason `removed`. A granted port that appears is claimed
- **Counters** - the worker counts bytes received from and written to each port and reports them once a second while they change
- **Default serial settings** - the worker keeps the last `defaults` message of the page and puts its content into every claim of a serial port as the field `defaults`. Before the page sent that message a claim has no `defaults`. A claim of a USB device never has it. The server uses the field only for a port it has no record of; see Default serial settings under Serial settings

## USB device in the worker

- Operations map one to one to WebUSB: `open`, `close`, `selectConfiguration`, `claimInterface`, `releaseInterface`, `selectAlternateInterface`, `controlTransferIn`, `controlTransferOut`, `transferIn`, `transferOut`, `clearHalt`, `reset`. Bulk and interrupt endpoints both use `transferIn` and `transferOut`
- **Descriptors** - WebUSB's parsed fields of the device and of its `configurations` (always available). Once the device is open, `raw` holds the device descriptor and every configuration descriptor as the device sent them (base64), read with `GET_DESCRIPTOR` control transfers. When the device refuses that read, `rawError` holds the browser's error and the `open` still succeeds
- **A pending IN transfer is kept** - WebUSB has no timeout. The worker ends the wait of a `transferIn` when `args.timeout` ms are over and answers `TimeoutError`. The transfer stays pending in the browser. The worker keeps that promise per device and endpoint and hands its result to the next `transferIn` on the same endpoint, so no packet is lost. That result can hold more bytes than the later call asked for, because the kept transfer has the earlier `length`. A `transferIn` that still waits when the next one arrives on its endpoint is answered `AbortError`. `close` and `reset` drop the kept transfers
- **Errors** - a rejected WebUSB call is answered with the `DOMException` name and message unchanged; a `stall` or `babble` status is answered as a result with that status
- **Removal** - as for a serial port, on `disconnect` and `connect` of `navigator.usb`

## Ownership

- One tab owns a device. A worker claims a key before it opens the device; the server refuses a claim on a key another connected tab holds and names that tab and the device
- The server broadcasts the whole device table to every tab on every change. A tab shows a device owned by another tab as held by the other tab and offers no Attach, Detach or Forget for it
- When the owning tab's WebSocket closes, its devices become `detached`. The virtual serial device, its path and its monitor buffer stay
- No automatic takeover: another tab offers **Attach** on a detached device it has a grant for
- **Detach and Forget** - for Detach the worker closes the device and releases it with reason `detach`; the grant stays. For Forget the worker closes the device, revokes the grant (`forget()` of the port or the device) and releases the device with reason `forget`
- **Release** - the server carries out a `release` with reason `detach` or `removed` only for the tab that holds the device. It carries out `forget` for that tab, and for any tab when the device is detached. `forget` removes the device from the table; its key keeps its name
- **Removed** - a device released with reason `removed` is `detached`, and its record has `error` `removed` until a tab attaches it again. The records have no field for a reason
- **Reconnect** - when its WebSocket closes, the worker keeps its ports open and connects again: after 0.5 s, then after twice the earlier wait each time, 10 s at most. It then claims every device again, except a device the user detached; that one is claimed again after a page load. A port that stayed open is not opened again. When the server refuses the claim, the worker closes the device

## WebSocket protocol

Endpoint `<base_url>jupyterlab-device-bridge-extension/ws`, `@ws_authenticated`. The page builds the URL, appends `?token=` when the lab's server settings carry a token, and passes it to the worker; cookies cover the rest.

**Binary frame** (both directions): byte 0 = `0x01`, bytes 1-2 = sid big-endian, rest = serial data. Tab → server is data received from the port; server → tab is data to write to the port.

**Text frame**: one JSON object with `type`.

| Tab → server      | Fields                                                                       | Meaning                                                                                                                                                                                                                                                   |
| ----------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hello`           | `tabId`, `serial`, `usb` (booleans: interface present)                       | first message                                                                                                                                                                                                                                             |
| `claim`           | `kind` (`serial` or `usb`), `key`, `info`, `defaults?`                       | ask to own a device; serial `info` = `{usbVendorId?, usbProductId?}`, USB `info` = `{vendorId, productId, serialNumber?, productName?, manufacturerName?}`; `defaults` = the default serial settings of the tab's lab, in the claim of a serial port only |
| `serial-state`    | `name`, `state`, `settings`, `signals`, `error?` (the browser's reason text) | the port's state changed                                                                                                                                                                                                                                  |
| `usb-descriptors` | `name`, `descriptors`                                                        | sent after a claim is granted and again after `open`; see Descriptors under USB device in the worker                                                                                                                                                      |
| `stats`           | `name`, `rx`, `tx`                                                           | byte counters                                                                                                                                                                                                                                             |
| `release`         | `name`, `reason` (`detach`, `forget`, `removed`)                             | the tab gave the device up                                                                                                                                                                                                                                |
| `ack`             | `seq`, `ok`, `result?`, `error?` (`{name, message}`)                         | answer to a server command                                                                                                                                                                                                                                |
| `request-result`  | `id`, `ok`, `name?`, `error?`                                                | outcome of a device request the user acted on                                                                                                                                                                                                             |
| `ping`            | `t`                                                                          | round-trip probe, every 2 s                                                                                                                                                                                                                               |

| Server → tab       | Fields                                                                   | Meaning                                                                                                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `welcome`          | `tabId`, `configs`, `deviceDir`                                          | answer to `hello`; `devices`, `requests` and `runs` follow it                                                                                                                                                           |
| `claimed`          | `key`, `ok`, `name?`, `sid?`, `settings?`, `heldBy?`                     | answer to `claim`; on `ok` the worker opens a serial port with `settings`; a refusal for a device another tab holds carries `name` and `heldBy`; any other refusal carries neither, and its reason is in the server log |
| `devices`          | `serial`, `usb` (lists of device records)                                | whole table, on every change                                                                                                                                                                                            |
| `requests`         | `pending` (list of `{id, kind, vendorId?, productId?, reason, program}`) | pending device requests, on every change                                                                                                                                                                                |
| `runs`             | `running` (list of run records)                                          | every live run, see Runs; after `welcome` and on every change                                                                                                                                                           |
| `serial-configure` | `seq`, `name`, `settings`                                                | reopen with these settings; sent only when they differ from the settings last sent, or when the tab last reported a state other than `open`                                                                             |
| `serial-signals`   | `seq`, `name`, `dtr?`, `rts?`, `brk?`                                    | set the control lines that are named with `true` or `false`                                                                                                                                                             |
| `serial-action`    | `seq`, `name`, `action`                                                  | run one action                                                                                                                                                                                                          |
| `serial-write`     | `seq`, `name`, `data` (base64)                                           | write bytes that did not come from the pty (CLI `monitor write`)                                                                                                                                                        |
| `usb`              | `seq`, `name`, `op`, `args`                                              | one USB operation; `op` is the name of the REST route and `args` carries WebUSB's parameter names; binary data is base64 in `args.data` and `result.data`; a `transfer-in` carries `args.timeout` in ms                 |
| `pong`             | `t`                                                                      | echo of `ping`                                                                                                                                                                                                          |

Every server command carries `seq`; the tab answers each with one `ack`. The server fails a command with no `ack` after its timeout: 5 s by default, and the caller's `timeout` for a USB operation. For a `transfer-in` the server waits 0.5 s longer than that, because the worker ends that wait itself.

`settings` = `{baudRate, dataBits, parity, stopBits}` with `parity` one of `none`, `even`, `odd`.

`defaults` = `{baudRate, dataBits, parity, stopBits, onOpen}` with the values a settings change takes. A claim with `defaults` that the server refuses is answered with `claimed` and `ok` false; see Default serial settings under Serial settings.

## Virtual serial device

- One pty pair per serial name at a time, created at the first claim, destroyed at `forget` and when the server process ends (an `atexit` hook). A pty that a tool left in exclusive mode is replaced; see Exclusive mode
- **Killed server** - a server that is killed (SIGKILL, out of memory) runs no hook and leaves its links and sockets. The next server that uses the directory removes them when it starts; see Lock under Device directory. Until then a left link can lead to another pty. A path is valid only for a device that `list` prints
- **Raw from the start** - the pty is set raw (no echo, no line discipline, no CR or LF translation) at creation and again after every tool close, with its speed set to the port's baud rate. For a new port that is the default baud rate of the lab, when the claim carried one. Without this the pty echoes port data back to the port
- **Open and close** - the server opens the slave once and closes it, so the master reports `POLLHUP` while no tool holds the slave. While no tool holds the device a 20 ms timer polls the master: `POLLHUP` cleared = a tool opened the device; `POLLIN` with `POLLHUP` = a tool opened the device, wrote and closed it between two polls. The master is registered with the event loop for reading only while a tool holds the device. The read that fails with `EIO` = the last tool closed the device and the server has read all that it wrote. A tool that opens and closes the device between two polls without writing is not seen, unless it runs with the shim and makes a call the shim passes on
- **Holder** - at open the server finds the process that holds the slave by scanning `/proc/<pid>/fd` of its own uid, and reports `pid` and program name
- **Baud** - before forwarding any chunk read from the master, the server reads the master's termios. A changed speed is sent as `serial-configure` before the chunk, so the bytes follow the reopen. While a tool holds the device the 20 ms timer reads the speed too, so the baud rate of a tool that only reads is applied. Speed 0 is a hang-up request and is ignored
- **`serial-configure`** - sent only when the settings differ from the settings the server sent last, or when the tab last reported a port state other than `open`: at tool open, at a baud change, at tool close, at a settings change and at a `T` line of the shim. While the device is detached the server only records the settings; the next `claimed` carries them
- **On tool open** - find the holder, send the port's settings with the tool's baud, then the port's action unless it is `none`. No flush: the slave's input queue is empty then
- **On tool close** - drop the queued bytes, set the pty raw at the port's baud rate, empty the slave's input queue (the server opens the slave for that moment), clear the holder and the frame format the shim reported, send the port's own settings (its baud rate included)
- **Exclusive mode** - when that open of the slave fails with `EBUSY`, a tool set `TIOCEXCL` and ended without clearing it. The device then takes a new pty: the symlink at the same path points to the new slave, and the shim socket moves to `pts-<new minor>.sock`
- **Port → tool** - forwarded only while a tool holds the device; always appended to the monitor buffer. Bytes that the tool has not read yet are queued in order, up to 8 MiB; bytes beyond that are dropped
- **Tool → port** - read in chunks of at most 64 KiB and sent as binary frames. Dropped while the device is detached

## Serial settings

A port has one settings record: `{baudRate, dataBits (7 or 8), parity, stopBits (1 or 2), onOpen}`; `onOpen` is one of the actions above.

The system delivers six read-only configs: `{id, name, system: true, baudRate, dataBits, parity, stopBits, onOpen}`. The first, `default`, holds the built-in values, so a port can always return to them.

| id                 | Settings   | onOpen           | For                                                    |
| ------------------ | ---------- | ---------------- | ------------------------------------------------------ |
| `default`          | 115200 8N1 | `none`           | the built-in values; a port with these values names it |
| `monitor`          | 115200 8N1 | `none`           | reading a board's output                               |
| `arduino-upload`   | 115200 8N1 | `pulse-dtr`      | Arduino Uno, Nano, Mega through the serial bootloader  |
| `arduino-isp`      | 19200 8N1  | `none`           | an Arduino used as ISP programmer; no reset on open    |
| `stm32-bootloader` | 115200 8E1 | `none`           | STM32 serial bootloader                                |
| `esp-upload`       | 115200 8N1 | `esp-bootloader` | ESP32 and ESP8266                                      |

- A user saves the current five values of a port under a name of 1 to 64 characters. The saved configs are `{id: "config-<8 hex>", name, system: false, ...five}` in `serial-settings.json` under `jupyterlab-device-bridge` in the Jupyter data directory, mode `0600`, written with a temporary file and `os.replace`. A name or id that matches a system config or a saved config, ignoring case, is refused
- A system config is never written: the user applies it to a port, changes the fields and saves the values under a new name, which makes a user-saved config
- Applying a config copies its five values onto the port and names it; changing a single field makes the port custom, with no config. Deleting a saved config that a port uses leaves the values and clears the config
- While a tool holds the device: baud rate = what the tool set; data bits, parity and stop bits = the port's, unless the shim reported the tool's own
- **Default serial settings** - a serial port that the server has no record of gets the five values of the claim's `defaults` over the built-in ones. The tab opens the port with the four settings, the pty starts at that baud rate, and `onOpen` of `defaults` is the action on open. A claim without `defaults` gives the built-in values. The port starts on the first system config in the list whose five values equal those of the port: with the built-in values that is `default`, not `monitor`, which holds the same values; `defaults` that match no system config leave the port custom
- **Check of `defaults`** - done before the key gets its name and before the device directory or the pty is made. The fields are `baudRate`, `dataBits`, `parity`, `stopBits` and `onOpen`, each optional, with the values `PUT serial/<name>/settings` takes. Any other field, a value outside these, or `defaults` that is no object refuses the claim: `claimed` with `ok` false, the reason in the server log, no record, no name for the key
- **New ports only** - a claim of a key that has a record ignores `defaults`, also `defaults` the server would refuse. So a changed setting of the lab changes no record. A forgotten device has no record: when it is added again it gets the `defaults` of that claim
- **One list of choices** - the five default settings in `schema/plugin.json` have the built-in values as defaults, and the `const` values of their `oneOf` entries are the choices of `serial_settings.py`. The baud rate is a whole number from 1 to 4294967295 in both files: the speed of the pty is a 32-bit field, and so is the baud rate of Web Serial. A pytest test compares the two files. A Jest test compares the `const` and the `title` of every entry with the value and the label of the same option in the Settings dialog of a serial row

## Preload shim

- **What** - a C library loaded with `LD_PRELOAD` that replaces `ioctl`, `tcsetattr` and `tcgetattr` for file descriptors that are a bridge pty, and leaves every other descriptor to libc
- **Finding the bridge** - `fstat` the descriptor; a pty slave with minor `N` is a bridge device when the socket `$JUPYTERLAB_DEVICE_SHIM_DIR/pts-<N>.sock` exists. The shim connects to that socket once per event. No socket = not a bridge device
- **Passed to the bridge** - `TIOCMBIS`, `TIOCMBIC`, `TIOCMSET` (DTR, RTS), `TIOCSBRK`, `TIOCCBRK`, and from `tcsetattr` the parity, data bits and stop bits. `TIOCMGET` and `tcgetattr` answer with what the tool last set
- **`tcsetattr`** - the shim first passes the call to libc with 8 data bits and no parity, the format a pty holds. So the baud rate reaches the pty and libc does not refuse the call. The shim then sends the tool's own format to the bridge, on every call
- **Socket protocol** - one line per event, the server answers `ok` after the tab acknowledged or after 1 s: `S <dtr 0|1> <rts 0|1>`, `B <0|1>`, `T <dataBits> <N|E|O> <stopBits>`. In a `T` line, data bits other than 7 or 8 and stop bits other than 1 or 2 keep the port's value. While a tool holds the device, the server reads the tool's baud rate at that moment and sends it with the format in the same `serial-configure`. At a line of the shim the server looks for the tool at once and does not wait for the 20 ms timer, so the settings and the action of the tool open leave before that line's event. A `T` line with no tool on the device changes nothing
- **Packaging** - the wheel carries the C source inside the Python package. `jupyterlab-device run` builds it with the system C compiler (`cc` or `gcc`) on first use into `~/.cache/jupyterlab-device-bridge/` (file name carries a hash of the source) and reuses it. `run` puts the library first in `LD_PRELOAD` and sets `JUPYTERLAB_DEVICE_SHIM_DIR` to `shimDir` of `GET status`. No compiler: `run` stops with a message that names the port's settings as the way that needs no shim. The wheel stays pure Python
- A statically linked tool does not load the shim; the port's settings must be enough for it

## Runs

A run is one process that `jupyterlab-device run` started. The panel lists the runs, starts one and stops one. The lab cannot find out that a tool needs the shim, because the pty refuses the tool's calls without telling the server; so the user starts a run when a tool needs one.

- **Record** - `{pid, program, command, device}`. `pid` identifies the run. `program` is the base name of the first word of the command, `command` is the words of the command joined with one space and cut after 200 characters, `device` is the `--device` of the run or null
- **Registration** - `jupyterlab-device run` posts `{pid, command, device?}` to `POST runs` after the shim is built and before it replaces itself with the tool; `pid` is its own process id and `command` the list of the tool's words. The call has a socket timeout of 2 s. The tool starts also when the call fails or is refused, and `run` prints nothing about it. `shell` posts the two words `jupyterlab-device shell` as its `command`, because the shell command of a lab can be a start script whose name does not say that the run is a device shell
- **Check** - the server takes a `pid` only of a live process of its own user: it reads `/proc/<pid>/stat`, compares the owner of `/proc/<pid>` with its own uid, and keeps the start time of the process (field 22) with the record. Any other `pid`, a `command` that is no list of 1 or more strings, and a `device` that is neither a text nor null, answers 400 `bad-request`. A second registration of a registered `pid` replaces the record. The server does not check that the process is a `jupyterlab-device run`: a caller that holds the server's token can register any process of the server's user, and such a caller can signal that process itself
- **Watch** - while at least one run is registered the server reads the start time of each run's process once a second. A process that is gone, that is a zombie (state `Z`), whose start time differs or that no longer belongs to the server's user ends the run: the record is removed and the list is broadcast. The watch is a timer of the event loop that is set only while a run is registered
- **Stop** - `DELETE runs/<pid>` checks the start time as the watch does, sends `SIGHUP` to the process, and sends `SIGKILL` 3 s later when that process still lives. The signal is `SIGHUP` and not `SIGTERM`, because an interactive bash ignores `SIGTERM`, and fish ends on `SIGTERM` without ending its foreground tool; both shells end on `SIGHUP` together with their jobs. A tool that `run` started ends with status 129. The signal goes to the process of the run only, not to its process group. The route answers 204 at once; the run leaves the list when the watch sees the process gone. An unknown `pid` answers 404 `unknown-run`. So does a run whose process the check finds ended or replaced: no signal is sent, and the run is ended as the watch ends it
- **Device shell** - `jupyterlab-device shell` is `run` with the tool taken from the server: the `shell` of `GET status`, which is the shell command of the lab's terminals. So a device shell is the shell that a terminal of the lab starts, with the shim. It takes no argument. The CLI does not read the variable `SHELL` for it: a lab can start its server without that variable, and neither bash nor fish gives it to the programs they start, so the line `jupyterlab-device run -- "$SHELL"` of the first version had an empty tool in such a lab. A server that reports no `shell` still runs the version from before an install: `shell` then ends with status 1 and one line that says to restart JupyterLab. A shell command that cannot be started ends it with status 127, as `run`, and the message names `jupyterlab-device status --json`, which shows the shell command
- **Banner** - before `shell` replaces itself with the shell it prints a banner on standard output when standard output is a terminal. `run` prints no banner, for any tool. So the terminal that Start opens shows it, and a tool that an agent starts prints nothing extra. `banner.py` draws it; `cli.py` passes the environment, the known tool names, the devices and the columns of `shutil.get_terminal_size()`. `banner.py` holds the characters of the logo as they are, while the source of the CLI stays ASCII for the agent. The banner is 75% of the terminal's columns wide, at least 45 and never wider than the terminal. It opens with DEVICE and BRIDGE in the ANSI Shadow block letters, one column in: on one row when the banner is at least 91 columns wide, else DEVICE above BRIDGE; a terminal of fewer than 45 columns gets no logo. Under the logo come an empty line and the name line `◆ jupyterlab-device <version>` with `device shell` at the right edge of the banner, an empty line, then four sections, each opened by a rule `── <title> ───` as wide as the banner, and a plain rule under the last:
  - **Environment** - the environment the shell starts in and its known upload tools, in the order avrdude, stm32flash, esptool, pio: `current environment with avrdude, esptool`, or `<name> (<project|global>) with <tools>` for an environment chosen in the selector. In the current environment the tools are those that `shutil.which` finds on `PATH` and in the directories that `pipx environment --value PIPX_BIN_DIR` and `uv tool dir --bin` print; in a chosen environment the tools of its `bin`. With no tool: the name, `No avrdude, stm32flash, esptool or pio on PATH.` and `Install one to make use of the device shell.`
  - **Devices** - one line for each device that is attached and has no `error`, serial devices first, in the order of the server's table: `● COM <path>` with `<baud> <data bits><parity><stop bits>  on open: <action>`, or `● USB <name>` with `<vid>:<pid>  <product name>`. When one of these lines would be wider than the banner, the information of every device stands on the line under it, 9 columns in. With no such device: `No device is attached. Add one in the Devices panel of the lab.` `shell` reads the devices with `GET devices` and the 2 s timeout of the registration; when that call fails, or its answer is no device table, the banner has no Devices section. A server that answers neither call delays the shell by up to 4 s
  - **Agent skill** - the name `jupyterlab-device-bridge-extension` and how an agent finds the skill: `✓ linked in ~/.agents/skills` or `~/.claude/skills` when that folder holds `jupyterlab-device-bridge-extension/SKILL.md`; `✓ listed by <skill folder>` when a `SKILL.md` one level under one of the two folders names the folder of the installed skill, as the GalaxaLab skill does; else `○ no agent finds it` and a line that names `jupyterlab-device help`, whose agent skill section has the link commands. Under it the path of the `SKILL.md` that the wheel installed under `sys.prefix`; when there is none, `not installed under <prefix>` in place of all of this
  - **Commands** - `list`, `settings apply <dev> <config>`, `monitor read <dev>`, `terminal <dev>` and `help`, each with what it does in one column; when one line would be wider than the banner, each description stands on the line under its command
- **Colours of the banner** - 24-bit colours from the palettes of `tui_theme`, dark or light after `tui_theme.pick_theme()`: `TEXTUAL_THEME`, the terminal's answer to OSC 11, `COLORFGBG`, then dark. The full blocks of the logo have a diagonal gradient from `cyan-bright` to `mint`, its box characters `subtle`, the colour of the rules; the diamond is `orange`; the text is `text`, a description `muted`, a command `cyan`. A device path or name has the hue `device` (`#9fe0ee` dark, `#0b6f8f` light), its information the hue `info` (`#a8dcc4`, `#2e7d5b`), and its lamp `mint`. The colour reset ends the banner, and one empty line follows it. With the variable `NO_COLOR` set to a non-empty value the banner holds no escape sequence and the background is not asked for. `tui_theme`, and with it Textual, is imported only for a banner with colour. The banner is written as UTF-8 bytes, because a text write fails where the encoding of standard output has no such characters, and the shell would then not start. The lookup of the environments and the selector come after the check of the shell command and before the registration of the run; the registration comes before the banner
- **Environment lookup** - `environments.py`, `Environment`, `current`, `find`, `activation`. Only `shell` looks, and only when standard input and standard error are terminals; `run` never does. Project: the directory `.venv` in the start directory (`os.getcwd()`), named `.venv`. Global: the environments of `conda env list --json`, with conda taken from `$CONDA_EXE` when it is set and not empty, also when that file does not exist, else `conda` on `PATH`, else `/opt/conda/bin/conda`; the name is `envs_details[prefix].name`, else the base name of the prefix. An environment is offered when its `bin` holds a known upload tool (`shutil.which` over that `bin`). Order: the project first, then conda in the order conda lists them. The environments that `CONDA_PREFIX` and `VIRTUAL_ENV` name count as the current environment and are not offered. The commands of the lookup (`conda`, `pipx`, `uv`) run with `NO_COLOR=1` and without `FORCE_COLOR`, because uv colours its output under `FORCE_COLOR`. A command that is missing, exits with a status other than 0, prints output that cannot be read, or runs over 5 s (`LOOKUP_S`) skips only its own source
- **Environment selector** - `env_picker.py`, `EnvironmentPicker` and `choose`: a Textual app that `shell` shows when the lookup offers at least one environment and standard input and standard error are terminals. Standard error counts because Textual draws on it. The theme comes from `tui_theme.pick_theme()` before the app runs and is applied in its constructor. Header row `jupyterlab-device  device shell` with `v<version>` at the right; the question `Start the device shell in which environment?`; under it the line `The shell starts with the bin folder of the chosen environment first on PATH and the variables that its activation sets. The first entry keeps the current environment.`; the first entry `current environment` with its tools, or `no upload tool`, then one entry per offered environment in columns: name, `project` or `global`, the tools joined with `, `. Enter (`Start the shell here`) starts the shell in the highlighted environment; Esc (`Keep the current environment`) and Ctrl+C keep the current one. The command palette is off
- **Chosen environment** - a conda environment puts `<prefix>/bin` first on `PATH` and sets `CONDA_PREFIX`, `CONDA_DEFAULT_ENV` and the variables of `conda env config vars list -p <prefix> --json`, for example `PLATFORMIO_CORE_DIR` of `firmware-avr`; an answer with a value that is not a text sets none of them. A `.venv` sets `VIRTUAL_ENV` and puts its `bin` first. The scripts of `activate.d` do not run, and the `bin` of the earlier environment stays on `PATH`. The start files of the user's shell run after this and can change `PATH` again; no test covers them
- **No modes** - a run loads every shim that exists. Today that is the preload shim for serial devices
- **Start in the lab** - the command `device-bridge:start-run` starts `jupyterlab-device shell` in a terminal of the lab. The lab calls the shell that this command starts a device shell. It types no line into a terminal: it calls the command `basic-terminal:launch` of `jupyterlab_basic_terminal_extension`, a dependency of the wheel, with `{argv, shutdownOnClose: true}`, `argv` the list of words to run. That command starts one program in a terminal with no shell around it, in the folder of the file browser, and closes the terminal's tab when the program ends. So after Stop or `exit` no shell without the shim is left. With `shutdownOnClose` true, closing the tab shuts the terminal session down (`DELETE api/terminals/<name>`), and that ends the program; so a closed tab of the serial terminal frees the port. The terminal extension honours `shutdownOnClose` from 1.0.9, the minimum the wheel requires
- **A launch that fails** - the list of words is a bash script and the command line: `/bin/bash -c <script> jupyterlab-device <word>…`, so the script has the command line as `"$0" "$@"`. The basic terminal extension needs `/bin/bash` on the server already. The script runs the command line and, when it ends with a status other than 0 less than 5 s after the script started, prints `Press Enter to close this terminal.` and waits for one line of input, so that a refusal of the CLI stays readable. It ends with the status of the command line. A bash that Stop ends less than 5 s after its start ends with status 129 and gets the prompt too; a fish that Stop ends exits with status 0 and gets none. The serial terminal command starts its command line the same way
- **No terminal to start it in** - where the server offers no terminals, or the lab has no command `basic-terminal:launch`, the lab shows the command line in a notification; in the second case the notification names the missing extension
- **A launch that is refused** - when the command `basic-terminal:launch` rejects, for example because the terminal ended before the lab displayed it, the plugin raises one error notification, `The terminal did not start: <reason>`, of at most 140 characters. The reason is the message of the rejection. For a refusal by the server of the terminal extension it is the code of that server, for example `invalid_cwd` for a folder of the file browser that no longer exists. Releases of the terminal extension before 1.0.8 gave such a refusal no text and the notification read `[object Object]`, and releases before 1.0.9 keep the program running when its tab closes, which is why 1.0.9 is the minimum. The lab shows a rejected command to nobody, so without this notification Start and Terminal would do nothing visible

## Monitor

- One ring buffer per serial name, `DeviceBridge.monitor_bytes` bytes (default 262144), with an absolute byte offset that only grows
- `GET serial/<name>/monitor?since=<offset>&wait=<seconds>` returns `{data (base64), start, next, dropped}`; `dropped` is true when bytes after `since` have already left the buffer. With `wait`, the call returns when new bytes arrive or the time ends
- The CLI turns that into last N lines and follow

## Device requests

- A program posts `{kind, vendorId?, productId?, reason, program}`; the server lists it as pending and broadcasts it
- The panel shows it and the lab raises a notification with a **Grant** button. The click is the user gesture; the main thread calls the grant dialog with that vendor and product filter. The notification is removed when the request ends or the WebSocket closes
- The tab answers with `request-result`. The server then sets the request's `state` to `granted`, with the attached device's `name`, or to `denied`, with the reason in `error` (`{name, message}`): Chrome's own when the dialog gave no device, the worker's when the server refuses the claim of the granted device. A dialog that Chrome did not open for lack of a user gesture leaves the request pending. A request with no answer gets the state `expired` after 300 s
- The caller polls `GET requests/<id>?wait=<seconds>`. No route ends a request: a request that its caller no longer waits for stays pending until it expires

## REST API

All under `<base_url>jupyterlab-device-bridge-extension/`, all `@tornado.web.authenticated`, JSON bodies.

| Method and path                                      | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET status`                                         | `{version, deviceDir, shimDir, shell, tabs, counts}`. `shell` is the list of words of the shell command of the lab's terminals: the `shell_command` of the server's terminal manager, and `[$SHELL]`, or `["/bin/sh"]` without that variable, where the server has no terminals. A tab is `{tabId, serial, usb, roundTrip}`. `roundTrip` is the server's own WebSocket ping to that tab in ms, sent when the tab's `ping` arrives; null until measured. `counts` is `{serial, usb, requests}`; `requests` counts the pending requests only                                                                                                        |
| `GET devices`                                        | `{serial: [...], usb: [...]}`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `GET settings-configs`                               | `{configs: [...]}`, the system configs first, then the user-saved ones                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `POST settings-configs`                              | `{name, baudRate, dataBits, parity, stopBits, onOpen}`; answers the saved config                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `DELETE settings-configs/<token>`                    | deletes a user-saved config; a system config is refused                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `PUT serial/<name>/settings`                         | `{config?, baudRate?, dataBits?, parity?, stopBits?, onOpen?}`; answers the serial record                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `GET serial/<name>/monitor`                          | see Monitor                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `POST serial/<name>/write`                           | `{data}` base64 → the port                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `POST serial/<name>/signals`                         | `{dtr?, rts?, brk?}`: one line or more, each `true` or `false`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `POST serial/<name>/action`                          | `{action}`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `GET requests`, `POST requests`, `GET requests/<id>` | device requests. In this order: `{requests: [...]}` with every request of the server's lifetime and its `state`; the new request record with its `id`; one request record                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `GET runs`, `POST runs`, `DELETE runs/<pid>`         | runs, see Runs. In this order: `{runs: [...]}` with every live run; the new run record; 204 after the stop signal was sent                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `GET usb/<name>`                                     | descriptors, as the tab sent them last                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `POST usb/<name>/<op>`                               | `op` is one of `open`, `close`, `select-configuration`, `claim-interface`, `release-interface`, `select-alternate`, `control-in`, `control-out`, `transfer-in`, `transfer-out`, `clear-halt`, `reset`. The body carries WebUSB's parameter names, binary data as base64 in `data`, and `timeout` in ms (absent or 0 = 5 s). The body of `open` also takes `program`, the name of the calling program, a text that is not empty; the server keeps it as `holder` of the record and does not pass it to the tab. Answers the result of the browser call: `{status, data}` for a transfer in, `{status, bytesWritten}` for a transfer out, else `{}` |

**Serial record**: `name`, `path`, `state` (`attached` or `detached`), `portState`, `tab`, `holder` (`{pid, name}` or null), `settings`, `configured`, `config`, `configName`, `signals`, `rx`, `tx`, `vendorId`, `productId`, `error`. `settings` is what the port is open with now; `configured` is the five configured values and `config` the applied config, or null for custom.

**USB record**: `name`, `state`, `tab`, `vendorId`, `productId`, `productName`, `manufacturerName`, `serialNumber`, `opened`, `holder` (`{name}` or null), `rx`, `tx`, `error`.

`holder` of a USB record names the program whose `open` opened the device. It is null while the device is closed, when that `open` named no program, after the device was removed and after its tab was lost.

`error` of a serial record is the browser's reason text of a port in the state `error`. In both records it is `removed` after the tab reported the device removed, else null.

**Errors**: `{error: {code, message, name?}}`.

| Status | Code                                               | When                                                                                                                                   |
| ------ | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `bad-request`, `bad-settings`, `invalid-name`      | malformed input, unknown action or unknown USB operation; unknown settings field or a value that the field does not take; invalid name |
| 404    | `unknown-device`, `unknown-request`, `unknown-run` | unknown device, request or run                                                                                                         |
| 409    | `detached`, `no-tab`                               | no tab holds the device; no tab is connected                                                                                           |
| 502    | `browser`                                          | the browser refused the operation; `name` and `message` are Chrome's own                                                               |
| 504    | `timeout`                                          | the tab did not answer in time, or a transfer in got no data within its timeout                                                        |

## Frontend

- **Commands** - `device-bridge:connect-serial`, `device-bridge:connect-usb`, `device-bridge:open-terminal` (`{name?}`; asks which port when several are attached; a name that is no attached serial port raises a notification and opens nothing), `device-bridge:show-panel` (label Show Devices Panel; toggles the option `showPanel`, see below), `device-bridge:start-run` (label Device Shell, caption `Open a device shell: a lab terminal in which tools control the lines of the serial ports`; see Runs); all in the command palette under `Devices`
- **Menu** - setting `showMenu` (boolean, default false). When true the lab shows a top-level **Devices** menu: Connect Serial Port, Connect USB Device, Serial Terminal, Device Shell, Show Devices Panel. The setting takes effect without a reload. The menu needs the lab's `IMainMenu` and `ISettingRegistry`; without one of them there is no menu
- **Option `showPanel`** - setting `showPanel` (boolean, default false). The Devices panel is in the left sidebar only while the option is true. The plugin applies the setting when it loads and on every change (`settings.changed`): it adds the panel with `shell.add(panel, 'left', { rank: 600 })`, or takes it out with `panel.parent = null`. A choice of the user in the lab (the command, the View menu item, the status bar item) is applied at once and saved after that; see the command below. There is one panel object for the life of the page. Hiding changes nothing else: the model, the worker, the attached devices, the status bar item and the notifications of device requests continue. Without the lab's `ISettingRegistry`, or when the settings fail to load, the option is kept in memory, starts false, and the command toggles it
- **Command `device-bridge:show-panel`** - `isToggled` returns the option. Executing it sets the option to the opposite value in this order: the panel is shown or hidden at once, then the plugin saves the value with `settings.set('showPanel', value)`. So the command and the Settings Editor are two controls of one stored value, and the panel does not wait for the save. When the command turns the option on it also opens the panel (`shell.activateById`), without waiting for the save. The plugin calls `commands.notifyCommandChanged` when the option changes, so the check mark of a menu item follows
- **A save that fails** - the panel stays as the user chose it, and the plugin raises one warning notification that says how the panel is now, names the setting `showPanel` and ends with the lab's reason. The promise of the command and of the status bar click never rejects. The server keeps the old value, and the next page load applies it. Before that, the next save of the plugin's settings decides what is stored: the setting registry of JupyterLab 4.6.4 changes its copy of the plugin's settings before a save and does not take the change back when the save fails. `registry.set` of another setting of the plugin sends that copy, so the choice is stored after all; a save of a settings text that holds the old value (`registry.upload`) stores the old value, and the panel follows it
- **View menu item** - `schema/plugin.json` adds the command to the View menu (`jupyter.lab.menus` → `main` → `jp-mainmenu-view`) with rank 9.97. In JupyterLab 4.6.4 that is the group of Show Notifications (9.92) and Show Log Console (9.95), between the separators at 9.9 and 9.99
- **Activation order** - `activate` is `async`. It first loads the settings of the plugin, when the lab has `ISettingRegistry`; then it builds the model with the default serial settings, and adds the panel when `showPanel` is true. The lab waits for the activation before it restores its layout, so the panel is in the sidebar before the restore, and the worker has the default serial settings before it claims the ports granted earlier. A settings load that fails is logged with `console.error`, and the plugin continues as without the registry
- **Layout restorer** - the plugin gives the panel to `ILayoutRestorer` (`restorer.add(panel, PANEL_ID)`) once, when the panel is shown the first time, not at activation. JupyterLab 4.6.4 puts every widget the restorer knows into a sidebar when the saved layout names it (`SideBarHandler.rehydrate`), also while the option is false. A panel the restorer does not know stays out
- **Default serial settings** - five settings: `defaultBaudRate` (integer, 1 to 4294967295, default 115200), `defaultDataBits` (7 or 8, default 8), `defaultParity` (`none`, `even`, `odd`; default `none`), `defaultStopBits` (1 or 2, default 1), `defaultOnOpen` (one of the five actions, default `none`). The four settings with fixed values give their choices as `oneOf` entries with `const` and `title`, not as `enum`: the Settings Editor shows a select with the titles and stores the `const`. The titles of the parity and of the action are the labels of the Settings dialog of a serial row (None, Even, Odd; Do nothing, Pulse DTR, Pulse RTS, Enter the ESP bootloader, Open at 1200 baud and close); the titles of the two integer settings are the numbers. The plugin reads them into `{baudRate, dataBits, parity, stopBits, onOpen}`, gives them to the model when it builds it and again on every change of the settings (`model.setSerialDefaults`). They reach the server in the claim of a serial port and apply to a port the server has no record of; see Default serial settings under Serial settings. Without the settings the model gets none, the claim has no `defaults`, and the server uses the built-in values
- **Panel** - a widget of the left sidebar, there only while the option `showPanel` is true: a header with the title `Devices` and the plus icon that adds a device; the section `Serial and USB` (`title` `Serial ports and USB devices of this computer`) with one row per device whose kind chip has a pale blue or pink tint, with border and text in the same hue at a shade the theme needs, or `No device attached` (its `title` keeps the sentence about the plus icon); the section `Requests` (`title` `Requests of programs in the container for a device`) with the pending device requests and Grant; the section `Device shells`; the footer `Round trip: <ms> ms` or `Round trip: not connected` (`title` `Round trip of a message from the browser to the server and back`), whose field `[data-field="round-trip"]` holds only `<ms> ms` or `not connected`
- **Absent interfaces** - when a browser interface is absent the panel shows `<names> need HTTPS or localhost, in Chrome or Edge`. The names are `Web Serial` and `WebUSB`, joined with `and`; with one name the verb is `needs`. Its `title` reads `The browser gives this page no access to <serial ports|USB devices|serial ports and USB devices>. Open the lab over HTTPS or at localhost, in Chrome or Edge.`
- **Plus icon** - an icon button in the panel header, `[data-action="add-device"]`, with the lab's own `addIcon` and the measures of the icon buttons of the AI assistants panel (`jupyterlab_ai_code_assistants_extension`): a hit box of 24 px by 24 px, a glyph of 14 px, no border, a transparent background, and `--jp-layout-color3` on hover. A click opens a menu (`MenuSvg`) below the icon, the left edges in one line, with the entries Connect Serial Port and Connect USB Device. The entries are the two connect commands of the application registry, so one command gives the label of the menu entry, of the palette entry and of the entry of the Devices menu. The menu has an entry only for an interface the browser has, and the icon is disabled when the browser has neither. The connect commands themselves are always enabled: in the palette and in the Devices menu a command whose interface is absent raises the notification that names HTTPS and `localhost`, which a user with the hidden panel needs. When the menu closes, the focus is on the icon again
- **Device row** - kind, name, state, the byte counters and the error text. The counters read `RX <bytes>, TX <bytes>`, each a count with its unit (`title` `Bytes from the device (RX) and to the device (TX)`): byte or bytes below 10,000, KB with one decimal from 10,000 to under 1,000,000, MB with one decimal from 1,000,000, and MB when the KB value rounds to 1000.0 (999,999 reads `1.0 MB`). A serial row adds the baud rate, the config (its name or `custom`), the action on open, the holder and the button Settings. A USB row adds the product, `Opened: yes` or `Opened: no` (`title` `Whether a program in the container has the device open`), and the name of that program or `none`. The state reads `attached`, `detached`, `held by another tab`, or `removed` for a detached device whose `error` is `removed`
- **Activity lamps** - each device row has two lamps, `[data-lamp="tx"]` and `[data-lamp="rx"]`: a small circle with the label `TX` or `RX` beside it. A lamp is lit while it has the attribute `data-lit`, and each event that lights it keeps it lit for 200 ms from that event. For a device this tab holds (`record.tab` is the tab's own id) the event is an `activity` message of the worker that names the device with that direction true; see Page and worker. So sparse traffic gives single flashes of 200 ms, bursts 400 ms apart give one flash each, and a period with bytes every 50 ms gives a steady light until 200 ms after the last such period, as the LEDs of a USB serial adapter do. For a device another tab holds, this tab's worker moves no byte of it, so the event is an update of the device table that carries a larger `tx` or `rx` counter than the row showed before; the first table of a row lights nothing. The `title` of a lamp reads `bytes to the device` or `bytes from the device`. A lit TX lamp is `var(--jp-error-color1)` and a lit RX lamp is `var(--jp-success-color1)`, fill and border; an unlit lamp has the colours of JupyterLab CSS variables
- **Row buttons** - **Settings** on every serial row. **Terminal** on an attached serial port, also on one that another tab holds. **Attach** on a detached device this tab has a grant for. **Detach** on a device this tab holds. **Forget** on a device this tab holds and on every detached device, also without a grant of this tab. Forget acts on the second click and ignores a second click within 500 ms of the first. Forget and Stop, when armed by the first click, show their label in `var(--jp-ui-inverse-font-color0)` on `var(--jp-error-color1)`
- **Settings dialog** - the button Settings (`[data-action="settings"]`, `title` `Change the serial settings and the action on open of this port`) opens `showDialog` of `@jupyterlab/apputils` with the title `Serial settings of <name>`, the body class `jp-DeviceBridgeSettings`, and the buttons Cancel, Delete config, Save as... and Save, each with the class `jp-DeviceBridgeSettings-button`; the four are 28 px high with 12 px side padding and 12.5 px text, 8 px apart in the footer. The body is a table with six rows, one setting per row: the row head is the label (Config, Baud rate, Data bits, Parity, Stop bits, When a program opens the port) with `scope="row"`, and the value cell holds the one control `[data-setting-field="config|baudRate|dataBits|parity|stopBits|onOpen"]` of one width and height; `tbody tr:nth-child(odd)` and `tbody tr:nth-child(even)` shade the rows through `--db-surface` and `--db-surface-hover`. The baud rate is one text field with `inputmode="numeric"` and a datalist of the standard rates 300 to 921600; a value outside that list shows the badge `[data-setting-badge="custom"]` in the same cell, and a standard value hides it. The config select holds `Custom` and every config of the server; choosing a config fills the five fields, and changing a field selects `Custom`. They are filled when the dialog opens from the record's `configured`; an update of the device table does not change an open dialog. Save sends one `PUT serial/<name>/settings` with `config` when the fields are the values of a chosen config, else each field that differs from `configured`; baud rate, data bits and stop bits are numbers. No request is sent when nothing changed, and Cancel sends nothing. Save as... asks for a name and sends `POST settings-configs` with the five values, applies the saved config and reads the list again. Delete config sends `DELETE settings-configs/<id>` for the user-saved config of the port and reads the list again. A refusal raises `Settings not changed: <reason>`, `Config not saved: <reason>` or `Config not deleted: <reason>`
- **Help document** - the Serial and USB header holds `[data-action="settings-help"]`, an accented `help` button at the far right. The file has no extension; `markdownviewer:open` names the Markdown Preview factory, so the lab opens the file as Markdown. The file is visible: a name that starts with a dot would hide it, but the contents API refuses a hidden path unless the server allows hidden files, and the server does not by default. A click reads that file through the contents API and writes it with `HELP_MARKDOWN` when it is missing or holds other text; an unchanged file is not written. The click then runs `markdownviewer:open` with the path, so the lab opens the file in its read-only Markdown Preview, not in a custom widget. The plugin does not set another title, because the lab treats the title of a document tab as the name of its file and renames the file when the title changes, which moves the file away from the path of the second click. The plugin finds the opened widget in the main area by its `content.context.path`; the lab gives the widget an id, and the plugin gives it the id `device-bridge-help` only when it has none. A second click finds the tab by the path and activates it, so the main area holds one help tab. A contents call that fails raises `The help document could not be opened: <reason>` and opens no tab

With no run it shows the text `No device shell opened`; its `title` reads `No device shell is open. Start opens a terminal in which tools control the lines of the serial ports.`
- **Run row** - `[data-run="<pid>"]` with the fields `[data-field="program"]`, `[data-field="pid"]` (`pid <n>`), `[data-field="command"]` and `[data-field="device"]`: the run's `device`, else the name of the serial record whose `holder.pid` is the run's `pid`, else `no device`. **Stop** (`[data-action="stop-run"]`) acts on the second click, as Forget does, and calls `DELETE runs/<pid>` through the model; a refusal raises `Not stopped: <reason>`

Its body lists each attached serial device as name and `path`, each attached USB device by name, and four example command lines, for avrdude, stm32flash, esptool and pio. The note of the body reads `Type a line in a device shell. The button Start of the section Device shells opens one. No line was run against a board.`

It is registered with priority 1, because the status bar hides an item of priority 0 in a narrow window
- **Serial terminal** - not a widget of this extension. The command starts `jupyterlab-device terminal <name>` in a terminal of the lab, as Start of the runs section starts its command line (Runs: Start in the lab, A launch that fails, No terminal to start it in); see Serial terminal below
- **Grant calls** - made only in the main thread, only from a command or a button handler. A `SecurityError` of a dialog becomes a warning notification that says to use the plus icon or Grant in the panel. The model takes every `SecurityError` as a missing user gesture: it chooses the reason from the name of the error and not from its message. The `GrantError` keeps the browser's message, and the warning does not display it. A dialog the user closed raises nothing. Any other failure of a dialog raises an error notification with the browser's text
- **Worker source** - one self-contained function `workerMain(scope)` in `src/worker.ts`; the worker is started from a Blob URL of that function's text, so the labextension serves no extra file. Jest calls `workerMain` with a simulated scope
- **Model** - `DeviceBridgeModel` in `src/model.ts` is the one object the widgets use. Its constructor takes the server settings of the lab and, optionally, the default serial settings; `setSerialDefaults` replaces them. It starts the worker, opens the grant dialogs and holds `interfaces`, `devices`, `tabId`, `configs`, `requests`, `runs` and `roundTrip`. `stopRun(pid)` calls `DELETE runs/<pid>`. `setSettings(name, change)` calls `PUT serial/<name>/settings`; `saveConfig(name, values)` and `deleteConfig(token)` call the settings-configs endpoints; `refreshConfigs()` reads the configs again. `hasGrant(name)` says whether this tab has a grant for a device of the table. While the WebSocket is closed, `devices`, `requests` and `runs` are empty and `roundTrip` is null
- **Page and worker** - page → worker: `start` (the WebSocket URL), `defaults` (`{serial: {baudRate, dataBits, parity, stopBits, onOpen}}`, the default serial settings; the model's constructor posts it before `start`, so the worker has it before it can claim a port, and `setSerialDefaults` posts it again; a model built without default serial settings posts none), `rescan` (after a grant dialog), `attach`, `detach`, `forget`, `request-result`. Worker → page: `welcome`, `devices`, `requests` and `runs` unchanged, `activity` (`{devices: [{name, rx, tx}]}` with `rx` and `tx` true or false: the devices of this tab that moved bytes from the device or to the device in the last 50 ms; the worker looks at its byte counters every 50 ms while it holds at least one open device, and posts the message only when a counter grew, so an idle tab posts nothing), `rtt`, `grants`, `closed`. `src/protocol.ts` holds the types
- **Styling** - class names `jp-DeviceBridge…`; colours only through JupyterLab CSS variables: the theme variables `--jp-*` and the material colour variables `--md-*`; the Extension Design System of the jupyterlab-extension skill
- **Texts** - English literals in the source; there is no translator. No text of the panel, of the lab commands, of the Info dialog and of the banner holds the word shim: they say device shell. The word stays in the documents and in `run --help`, where it names the library. The panel is hidden by default, so a text that sends the user to the Devices panel names the menu item. The item is a toggle, which takes a panel that is in a sidebar out of it, so each text names the item for a panel that no sidebar has: `(if no sidebar has the panel: View → Show Devices Panel)` in the notification of a terminal without a port, `(if no sidebar has it: View → Show Devices Panel)` in the notification of a dialog without a user gesture, which has 140 characters with it, and `(if no sidebar has the panel: menu View, item Show Devices Panel)` in the CLI and in the agent skill, which hold ASCII only; the one output of the CLI with other characters is the banner of a shell with the shim, see Runs. The texts inside the panel and the tooltip of the status bar item do not name it
- **Notifications** - every notification of the plugin and of the panel is raised with `autoClose: false`: the lab displays it as a toast that stays until the user closes it. Without `autoClose` JupyterLab 4.6.4 adds a notification to its list, raises the count of its status bar item and displays no toast. The lab cuts a notification text after 140 characters, so a text has its fixed part first and a reason of unknown length last, and the two texts without a reason have at most 140 characters

## Serial terminal

- **The extension's own app** - a full-screen Textual app, `terminal_app.py`, class `SerialTerminal`, with the settings screen `SettingsScreen`. `textual` (`>=8.2,<9`) and `pyserial` are dependencies of the wheel. `textual` is imported only by the command `terminal`
- **`jupyterlab-device terminal <name> [--baud N]`** - reads the record, refuses a device another program holds (exit 1, names the program), refuses to start without a terminal on standard input and standard error (exit 2, names `monitor read` and `monitor write` for an agent), because the app would wait for keys that never come and hold the device; chooses the theme with `tui_theme.pick_theme()`, then runs the app in the same process; it replaces itself with no other program and prints nothing before the app starts. Exit 0 after Ctrl+Q or Esc; exit 1 when the path cannot be opened, with `jupyterlab-device: cannot open <path>: <reason>`. It does not check that the device is attached
- **An ordinary tool on the virtual device** - the app opens the path with pyserial (`serial.Serial(path, baud)`), so the bridge shows the CLI process as the holder, runs the port's action on open, and the monitor buffer records every byte. One thread reads (0.05 s timeout) and one thread writes, in the order of sending. Every call to the bridge (record, `set_settings`, signals, action) runs in a thread. The record is read every 0.5 s
- **Screen**, top to bottom - the header row `jupyterlab-device terminal · <name> <path> · <baud> <data bits><N|E|O><stop bits> · DTR on|off|- RTS on|off|- · RX <n> TX <n>` with `v<version>` at the right; RX and TX count this terminal's bytes, and `-` is a line the port has reported no state for. The traffic view: one line per received line, per 256 bytes or per pause of 0.05 s, and one line per sent block, `HH:MM:SS.mmm RX|TX <body>`, RX amber and TX cyan, the body as text with control bytes as `\xNN` or as hex digits like `41 42 43`; the last 5000 lines are kept. The status line: the state, `attached` in mint or `removed - <reason>` in rose, then the last message, rose for a refusal. The send row: `send text LF >` or `send hex >` and the input field. The key line
- **Keys** - the key line lists them: `^q` quit, `esc` quit, `^o` settings, `^x` text/hex, `^p` pause, `^l` clear, `F2` DTR on/off, `F3` RTS on/off, `F4` break (`brk` true, 0.25 s, `brk` false), `F6` pulse DTR (`pulse-dtr`), `F7` pulse RTS (`pulse-rts`), `F8` ESP bootloader (`esp-bootloader`), `F10` 1200 baud touch (`touch-1200`), `^c` sends the byte 0x03 and does not quit, `^y` shows the key help. Enter sends the input line. The first press of `F2` or `F3` on a line with no reported state sends false. The board actions are on function keys, because the send field keeps the editing keys of Textual's input (Ctrl+A, Ctrl+E, Ctrl+D, Ctrl+U, Ctrl+K). No key that the browser or the lab takes is used (F1, F5, F9, F11, F12, Ctrl+W, Ctrl+T, Ctrl+N, Ctrl+R). On the settings screen only its own keys, Tab, Shift+Tab, Ctrl+Q and Esc act
- **Key help** - `KeysScreen`: Ctrl+Y opens a screen that lists Enter and each binding of the app with what it does (`KEY_HELP`); Esc or Ctrl+Y closes it. F1, the usual key for help, is taken by the browser, and the lab's terminal (xterm.js) sends no byte for Ctrl+/; it sends a control byte only for Ctrl with a letter, Ctrl+Space and Ctrl+3 to Ctrl+8. Of the letters, Y is the one that neither the app, the editing keys of the send field, the browser nor the lab takes; Ctrl+Z stays free for its usual meaning. While the key help shows, only Ctrl+Q and Ctrl+Y act
- **Settings screen** (`^o`) - baud rate (a whole number from 1 to 4294967295, else `refused: the baud rate is a whole number from 1 to 4294967295`), data bits 7 or 8, parity none, even or odd, stop bits 1 or 2, line ending none, LF, CR or CRLF (default LF), send the typed line as text or hex. Tab moves, arrows move within a row, Space chooses, Enter applies, Esc cancels. Applying sets a changed baud rate on the path with pyserial, because the bridge takes the baud rate from the program that holds the device, and sends the changed serial fields through `PUT serial/<name>/settings`; so the port reopens without a restart of the terminal and the record lists the values. A change of the line ending or of text or hex alone sends nothing to the bridge. Status `settings 9600 8E1 applied`
- **Sending** - text mode sends the line plus the line ending; hex mode sends the bytes written as hex digits with no line ending. Invalid hex: `refused: '<input>' is not bytes written as hex digits, for example 7f 00 a5; nothing was sent`, and the input stays. While the state is removed nothing is sent: `removed: nothing was sent`
- **Removed** - a detached, removed or forgotten port, or a failed read or write of the path, leaves the app open with the state `removed - <reason>` in rose: `removed - the browser no longer lists the port`, `removed - no lab tab holds the port`, `removed - the device path failed: <error>`. Sending stops until the record is attached again; a failed path stays removed
- **Themes** - `stellars-tech-dark` and `stellars-tech-light` from `tui_theme.py`, chosen at start: `TEXTUAL_THEME`, else the terminal's answer to OSC 11, else `COLORFGBG`, else dark. Every colour comes from the `$st-*` variables or `tui_theme.color()`. The command palette is off
- **In the lab** - the command `device-bridge:open-terminal`, the Devices menu entry and the **Terminal** button of a serial row start that command line in a terminal of the lab through `basic-terminal:launch` with `shutdownOnClose: true` (Runs: Start in the lab); the terminal's tab closes when the app ends, and closing the tab ends the app and frees the port

A failed `jupyter server list --json` (a timeout, a missing `jupyter`, a status other than 0 or a line that is not a record) is tried up to 3 times, with a 1 s pause between attempts, and then refused with its reason; only a successful list with no matching record falls back to `JUPYTER_PORT`. With no matching record, the address comes from `JUPYTER_PORT` (default 8888) and `JUPYTERHUB_SERVICE_PREFIX`. Hub token first, then the listed token, then `JUPYTER_TOKEN`; requests go to `127.0.0.1` without a proxy.
- Exit status: 0 done; 1 not done, with the reason on stderr; 2 wrong arguments, and for `request` nobody answered in time; 130 on Ctrl+C. `run` exits with the tool's status, or 127 when the tool cannot be started. `shell` exits as `run` does, with the shell's status. `terminal` exits 0 after Ctrl+Q or Esc, 1 when the device is held or its path cannot be opened, and 2 without a terminal

- **Examples in `--help`** - the top-level `--help` ends with one example command line for each known upload tool that `shutil.which` finds on `PATH` when the help is printed: `avrdude -c arduino -p atmega328p -b 115200 -P <path> -U flash:w:firmware.hex:i`, `stm32flash -b 115200 -w firmware.bin -v -g 0x0 <path>`, `esptool --port <path> write-flash 0x0 firmware.bin` and `pio run -t upload --upload-port <path>`. Outside a device shell (the variable `JUPYTERLAB_DEVICE_SHIM_DIR` is not set) the stm32flash, the esptool and the pio line carry the prefix `jupyterlab-device run --device <name> -- `, as in the README. `<path>` stands for the path that `jupyterlab-device list` prints; the help makes no call to the server. A tool that is not found is not listed. With none found the help reads `No upload tool is on PATH. Known tools: avrdude, stm32flash, esptool, pio.` The examples are made when the parser is built, which `main` does directly before it prints the help. The sentence above the example lines says that `<path>` is the path of the serial device, which `jupyterlab-device list` prints. So the help differs between two shells with different `PATH`, for example before and after a conda environment is activated
- **PlatformIO in `run --help`** - pio does not find the virtual device by itself: name its path with --upload-port for an upload and with --port for pio device monitor, or set upload_port and monitor_port in platformio.ini. `run --help` says so, has the example `jupyterlab-device run --device tty-2341-0043 -- pio run -t upload --upload-port /run/devices/tty-2341-0043`, the line `pio device monitor --port /run/devices/tty-2341-0043 --baud 115200`, which needs no `run --`, and the two keys of `platformio.ini`; the README section Working with an AI agent has the same in its subsection PlatformIO

The command restores the configured values and, when the port was open, waits up to 2 s for it to be open again, also when the sweep stops or no rate is readable. The tool probes start `avrdude -c arduino -p atmega328p -b 115200 -P <path> -U signature:r:-:h`, `stm32flash -b 115200 -m 8n1 <path>` or `esptool --port <path> chip-id` through `run --device`, so the tool gets the shim. A tool that is not on PATH is a failure whose next step names the installer script in `envs` beside the agent skill. With no DEVICE and one attached port the probe uses that port; a detached port names reattach and the config apply; several attached ports and no DEVICE are refused with exit 2

## Python client and pyusb backend

- `pyserial` and `textual` are runtime dependencies for the serial terminal; `textual` also draws the environment selector of `shell`. The bridge itself imports neither
- `jupyterlab-basic-terminal-extension` is a runtime dependency for the two commands of the lab that start a terminal; no Python code of this extension imports it, and the frontend names only its command id `basic-terminal:launch`
- `jupyterlab_device_bridge_extension.client` - `DeviceBridgeClient` (same discovery as the CLI) with `status()`, `devices()`, `configs()`, `save_config()`, `delete_config()`, `serial(name)`, `usb(name)`, `request_device()` and `request_state()`. Its `program` is the name the bridge shows for the caller, in a device request and as the holder of a USB device it opened: the `program` given to the constructor, else the name of the running program. The CLI gives `jupyterlab-device`. `SerialDevice` has `record()`, `set_settings()`, `monitor()`, `write()`, `signals()` and `action()`. `UsbDevice` has one method per operation, and `control()` with a `bmRequestType` byte as in libusb
- **Client errors** - a failure raises `DeviceBridgeError` with `status`, `code`, `name` and `message`; for a browser error `name` and `message` are Chrome's. A transfer that the device ends with `stall` or `babble` raises it with that word as `name` and with `status` 200, because the HTTP answer was 200
- **Client timeouts** - `timeout_ms` of 0 or None means the bridge's own 5 s
- `jupyterlab_device_bridge_extension.pyusb_backend` - `get_backend()` returns a pyusb `IBackend` over the client; `install()` makes it the backend that `usb.core.find` and `libusb_package` hand out, for programs that do not take a backend argument. pyusb is imported only inside this module and is no dependency of the wheel
- **Backend descriptors** - the backend reads the device and configuration descriptors itself with `GET_DESCRIPTOR` control transfers, once per device name, and does not use `GET usb/<name>`. For that read, a search opens each attached USB device that is closed and closes it again
- **Backend errors** - a stall is a `USBError` with `EPIPE`, status 504 is a `USBTimeoutError`, any other failure is a `USBError` with `EIO`

## Tests without hardware

- **pytest** - real ptys, a real compiled shim, and `tests/fake_tab.py`: a WebSocket client that plays the browser tab (echo port, recorded settings and signals, a USB device that answers control and bulk transfers). The fixtures are in `conftest.py` at the repository root. The CLI runs as a child process. The serial terminal app runs headless with Textual's `run_test` against the real pty and the fake tab, and the environment selector with `run_test` alone; the real `terminal` command also runs on a pty as its terminal. `pio device monitor` runs for real where pio is installed (`~/.cache/conda/envs/firmware-avr`), else its test is skipped; the pio upload runs with a stand-in program for pio
- **Jest** - `src/__tests__/sim.ts` simulates `navigator.serial`, `navigator.usb`, the WebSocket with the server behind it, and the worker scope; `workerMain` runs against it. A simulated port can transmit with a delay and then discards at `close()` what it has not transmitted, as the specification says. The specs of the model, the plugin and the panel run the real `workerMain` on that scope too. The specs of the plugin and the panel replace the lab's packages by recorders
- **Galata** - one plain script simulates `navigator.serial` and `navigator.usb` in the page (init script) and in the worker (the test wraps `Worker` so the worker loads the simulation first, then the real Blob through `importScripts`). The page and the worker simulation share grants and recorded calls over a `BroadcastChannel`. Tests drive the real panel, the real worker, the real server, the real CLI and a small Python tool that opens the virtual device. The simulated grant dialog refuses outside a user gesture. The test server has its own runtime directory and device directory, and the hub and token variables are removed, so the real CLI finds that server only. The suite needs a C compiler for the shim. The panel is hidden with the default settings, so every spec that works in the panel starts with `showPanel` true through Galata's settings mock (`PANEL_SHOWN` in `helpers.ts`), and a second tab gets the same mock. Galata keeps the settings of such a page in memory, so no test writes a setting to the test server; the tests of the option itself run with the default settings
- Every test title starts with the id of the criterion it proves. Two tests have no id: `test_cli_signals_and_action_reach_the_port`, because no criterion names `signals` and `action`, and the template's activation test in `ui-tests/`
- No upload tool is installed, so no real tool completes an upload against a simulated bootloader in this version
