# FAQ

One row per symptom: the probe command, the cause it names and the next step. Probe before retrying a command. The probe group is `jupyterlab-device probe` with the subcommands `baud`, `avr`, `stm32` and `esp`; each probe ends with a `next:` line that names a command. Flags and output of every command: `jupyterlab-device --help`, `jupyterlab-device <command> --help`.

| Symptom | Probe | Cause | Next step |
| --- | --- | --- | --- |
| A refused run | `jupyterlab-device list`, `jupyterlab-device status` | The command says `is detached: no lab tab holds it`: no lab tab holds the port, or the tab that held it closed. `status` shows no connected tab, or a tab whose browser lacks Web Serial | Ask the user to attach the port again: the Attach button on its row in the Devices panel (if no sidebar has the panel: menu View, item Show Devices Panel). Run `list` until the line says `attached`, then start the run again |
| No serial data | `jupyterlab-device probe baud <device>`, `jupyterlab-device list` | The port is `detached` or carries `error:`, the board sends at another rate, or the tool reads another port | Set the rate the probe reports with `jupyterlab-device settings set <device> --baud <rate>`, reset the board, then `jupyterlab-device monitor read <device> --follow --timeout 10`. A detached port first needs the attach step of the refused run row |
| A wrong bootloader baud | `jupyterlab-device probe avr <device>` | The bootloader talks at another rate than the config: the old Nano at 57600, the new Nano at 115200. The rate that returns a device signature is the bootloader's rate | Upload with the avrdude form that matches the rate: `-b 57600` for the old bootloader, `-b 115200` for the new one, as `boards.md` shows. Keep `upload_speed` matched in `platformio.ini` |
| A pty that refuses parity | `jupyterlab-device settings show <device>`, `jupyterlab-device probe stm32 <device>` | A tool that sets parity on the path itself, for example stm32flash with its default 57600 8E1, gets EINVAL from the pty, which holds no parity | Start the tool under `jupyterlab-device run --device <name> --`, which passes parity to the browser, or run `stm32flash -b 115200 -m 8n1` and let the `STM32 bootloader` config supply 8E1 on the wire |
| Binary monitor output | `jupyterlab-device monitor read <device> --raw --lines 32` | The rate is wrong, so bytes decode as garbage, or the port carries binary data, for example an ESP32 console on UART0 | Set the correct rate, or capture the bytes into a file with `--raw`; for an ESP32 move the console to USB Serial/JTAG as `boards.md` says |
| A removed port | `jupyterlab-device list` | The browser no longer lists the port after a reset, a re-enumeration or an unplug; the line says `error: removed` | Ask the user to reconnect or reset the board, then apply a config again with `jupyterlab-device settings apply <device> <config>` and run `list`. Upload only when the line carries no `error:` |
| A held port | `jupyterlab-device list` | One program holds a serial device at a time; the line names `held by <program> (pid <pid>)` | Wait for that program or stop the run in the Devices panel. `monitor read` and `monitor write` do not open the port and work while it is held |
| The ESP8266 erase fails with esptool 5.6 | `jupyterlab-device probe esp <device>`, then `esptool --port <path> flash_id` | esptool 5.6 fails this chip's erase with `C400 Failed SPI operation in stub` and `0x0106` from the ROM. esptool 4.11 passes at the same offset, so the tool version is the variable, not the bridge | Use esptool 4.11 from PlatformIO's `tool-esptoolpy` with the `ESP upload` config and `--before no_reset`. The commands are in `boards.md` |
| `KeyError` on a record field, or `404` with `no device bridge`, after `make install` | `jupyterlab-device status`, `jupyterlab-device --version` | The installed package is newer than the running JupyterLab server, so the server still runs the old code and routes | Restart JupyterLab, then run the command again |
| A verified ESP32 upload leaves the board in download | `jupyterlab-device monitor read <device> --lines 20` | The USB-JTAG maps DTR to the IO0 boot strap, so the post-upload reset can come up as `boot:0x4 (DOWNLOAD(USB/UART0/1))` with `waiting for download` | Replug the USB cable or press RESET, then read the monitor again. `boards.md` has the line states |
| `pio run -t upload` fails with `Multiple ways to build the same target` | the pio output | A stale `.pio/build` after a framework change references two copies of the same source | `pio run -t clean` in the project, then the upload again |
| stm32flash times out on a Nucleo even with BOOT0 high | `jupyterlab-device probe stm32 <device>` | The STM32L1 bootloader uses USART1 PA9/PA10 or USART2 PD5/PD6, not the ST-Link VCP's PA2/PA3 | Use a USB-UART adapter on PA9/PA10, or another board; `boards.md` has the wiring |
